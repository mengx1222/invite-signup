## 一、核实为真并已修复

### 1. `api_trace` 把活 token 带进了"复制发给我"的诊断块

**评审来源**：四（P0，称 15 分钟可修）

**核实**：属实。`runner.py` 的 `on_response` 抓的是完整 URL：

```python
result.api_trace.append(f"{resp.request.method} {resp.url} -> {resp.status}")
```

而 `flow.py` 把它放进返回的 `trace`，Web UI 的 `buildDiagnosis()` 又渲染进诊断块。验证请求形如
`/api/auth/verify-email?token=<JWT>`，**这个 token 当时仍然有效**。台账做了值级脱敏，trace 没有——
于是"专门给人分享"的那块，成了唯一泄漏的地方。

**修复**：新增 `ledger.scrub_url()`，在记录点就脱敏，保留 path（读的人需要它）、丢掉凭据。

### 2. `verdict → 错误分类` 把"这站可能不是邀请制"判成"站点拒绝你，整批停"

**评审来源**：四（P1）

**核实**：属实。`failures.py` 的 `SITE_REJECTED` 词表里有 `"invite code"`，于是探站自己产出的
`"no invite code was found on this page"`（一条 **config** 发现，意思是"这页可能根本不是邀请页"）
命中了它，被判成 `site_rejected / abort`——"站点拒绝了你，停掉整批"。

原因和下一步动作都错了：读者会去找一个没坏的链接。

**修复**：把 `"invite code"` 换成更具体的 `"invite code is invalid" / "expired" / "not found"`，
并把探站那句话显式归入 `CONFIG`。实测：

```
no invite code was found on this page  -> config/stop          （原来 site_rejected/abort）
invite code is invalid                 -> site_rejected/abort  （不变）
```

### 3. 重定向链上的 `Set-Cookie` 被漏检

**评审来源**：四（P0）

**核实**：属实。`probe.py` 用 `r.cookies` 读 cookie，而 `requests` 的 `Response.cookies` **只含最终那个响应**。
邀请归因非常常见的做法就是 302 跳转前种 cookie——那样这里会完全漏检，`infer_attribution` 退化成从
HTML 里猜，而 docstring 明说"Set-Cookie header 是权威来源"。

**修复**：改用 `requests.Session()` 并读 `session.cookies`，同时记录跳转跳数。

### 4. GuerrillaMail 分页参数语义用错

**评审来源**：四（P0）

**核实**：属实。`seq` 是"上次见到的最后一条 `mail_id`"，不是累计条数。按条数累加会在 id 不连续时
跳过邮件或提前终止。

**修复**：`seq = batch[-1]["mail_id"]`。

### 5. `_persist()` 没把 `failure_kind / failure_action` 写进台账

**评审来源**：四（P1）

**核实**：属实，而且这是个"说了没做"的小谎言。`_classify_outcome` 的 docstring 写
"Recording it means the decision is visible in the ledger"，但 `_persist` 的 payload 里没有这两个字段，
只有散文 `last_error`。批量驱动读台账时得重新对散文做 `classify()`——分类规则一演进就会和当初不一致。

**修复**：写进台账。

### 6. 密码用 `random` 生成

**评审来源**：三（P0）

**核实**：属实。`make_password()` 用 `random.choice`。`random` 是 Mersenne Twister，输出可预测，
不适合生成凭据。

**修复**：改用 `secrets`，并用 Fisher–Yates + `secrets.randbelow` 打乱，避免"必含字符"的位置可预测。

### 7. 版本号两处漂移

**评审来源**：四（P1）

**核实**：属实。`__init__.py` 写 `0.1.0`，`pyproject.toml` 写 `0.2.0`。

**修复**：`__version__` 改为从已安装元数据读，回退到解析 `pyproject.toml`。现在只有一个事实源。

### 8. `from_dict` 对子结构不做字段过滤

**评审来源**：四（P1）

**核实**：属实。外层 dataclass 过滤了未知字段，`Attribution(**attribution)` 和
`Verification(**verification)` 没有。手写 profile 多一个旧字段就 `TypeError` 崩在加载阶段。

**修复**：抽出 `_only_known()`，三个层级一致。

### 9. `pick_link` 选不出链接时干等到超时，报错误的原因

**评审来源**：四（P2）

**核实**：属实。信到了、dump 里也有，但链接不含任何 hint 时，poll 继续空等到超时，
最后报"没等到邮件"——**和实际原因相反**。

**修复**：记住"信到了但没匹配上"，超时时明确说明，并给出第一条链接的样子。

### 10. 两套邮箱拒信词表各自维护

**评审来源**：四（P1）

**核实**：属实。`failures.py` 和 `runner.py` 各有一份，且已经漂移（一个写"邮箱域名"、一个写"邮箱"）。
这正是本项目在别处反复批评的重复。

**修复**：收敛到 `failures.py`，`runner.py` 改为 re-export。

### 11. `scrub` 的规则用下标分发

**评审来源**：四（P2）

**核实**：属实。`_VALUE_PATTERNS` 与替换模板靠 `index == 0 / 4 / 5` 配对，插入一条新规则就会整体错位。

**修复**：改成 `(pattern, replacement)` 成对结构，测试断言每条规则都自带替换。

### 12. README 里"66 个测试"与 badge 的 199 矛盾

**评审来源**：一、三、四（都说 P0）

**核实**：属实。第 42 行还写着 66，而 badge 与测试章节是 199。

**修复**：删掉那个硬编码数字，只保留一处事实源。

### 13. `import queue` 未使用、`cli` 里冗余的第二次 `decide()`

**评审来源**：四（P2）

**核实**：属实。第二次 `decide` 传的参数与第一次相同，只可能和自己矛盾。

**修复**：都删了。

## 二、核实后**不成立**的建议

这一节和上一节同样重要：照单全收会引入不必要的复杂度。

### `runner` 缺少对 verdict 的强制校验（评审二，称 P0）

**不成立。** 评审二说"如果 runner 在收到 profile 后直接开跑，而没有在入口处强制校验 verdict，
那么绕过 CLI 直接调用库函数的路径都可能跳过安全边界"。

实际代码 `runner.py:223`：

```python
verdict = decide(profile, tos_forbids_automation=tos_forbids_automation)
result.verdict_state = verdict.state
if not verdict.allowed:
    result.stage = "blocked-by-verdict"
    result.errors.append(verdict.summary())
    return result
```

**这条边界本来就在 runner 里，不在 CLI 里**。直接调用 `run_registration()` 同样会被挡住。
评审二的前提是"文档没说清"，这点它说对了一半——但结论"代码可能没有"是错的。

### 需要引入 SQLite / 跨进程文件锁（评审三，称 P1）

**不成立（至少现在）。** 项目明确只支持**单任务**：Web 端第二个请求直接 409 拒绝，不排队。
台账的并发风险只存在于同进程多线程（Web 每请求开一个 Ledger），而这个已经用按路径共享的锁解决了
（实测 4 线程各写 50 行 = 200/200）。

引入 SQLite 会带来 schema 迁移、事务边界、备份策略，而当前没有多进程写入的需求。
这是"为了看起来专业而引入技术"的典型例子——评审三自己在结尾也反对这么做。

### `create_preferring()` 是死代码（评审四，称 P2）

**不成立（已修）。** 这条在**上一轮**就已经修了：`runner.py:288` 现在会读 `profile.mailbox_prefer`
并调用它。评审四读到的是旧版本。

### `--wait-link` 只覆盖 link 模式，需要 `--wait-code`（评审四，称 P2）

**建议成立，但暂不做。** 理由：`mode="code"` 的 OTP 路径**至今没有真实站点样本**。
在没有样本的情况下设计半自动接口，等于猜接口形状。这条记入待办，等第一个 code 型站点出现时再做。

### 探站器需要 `GET/HEAD` 方法级拦截（评审二，称 P1）

**部分成立，但优先级低于看起来的样子。** 探站确实会发一个 POST（邮箱存在性检查），
所以"只允许 GET/HEAD"不能直接照做。真正的价值在于"让只读成为可审计的事实"，
这需要先定义清楚哪一次写是允许的。当前 `--no-advance` 已经能关掉那次检查。
这条留作改进项，不在本轮做。

### `blocked-by-tos` 需要版本化证据链（评审一，称 P0）

**方向对，但属于产品决策而非缺陷。** 评审一要求 `tos_evidence{url, fetched_at, content_hash, ...}`。
这在多用户产品里是必要的；对个人工具，"人显式声明"已经是可接受的边界，而且比自动抓取条款更保守。
记入待办，等真的多人使用时再做。

## 四、接受但暂不做的（附理由）

| 建议 | 为什么先不做 |
| :--- | :--- |
| 引入 SQLite | 单任务模型下没有多进程写入需求；会引入迁移与备份成本 |
| `--wait-code` | 没有 code 型真实站点样本，现在设计等于猜接口 |
| 把 `probe.py` 拆成包 | 46 KB 确实偏大，但拆分会产生大量无收益的抽象；等下一个真实站点暴露接缝再拆 |
| CI（GitHub Actions） | **认可，值得做**；本轮先修正确性，CI 作为下一轮的第一项 |
| 引入 Pydantic | dataclass + 显式 `_only_known()` 已覆盖当前需求，换框架收益不足以抵消改动面 |
| `automation_risk` 软信号 | 有价值，但需要先确定"记录但不作为阻断"的语义，避免又造一个没人读的字段 |
